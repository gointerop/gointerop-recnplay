O problema

Duas integrações morreram.
As duas no mesmo lugar.

Não foi no FHIR. Não foi no protocolo. Foi em entender o cadastro.

Pegava-se a documentação do fornecedor, montava-se o de-para numa planilha, e quando rodava com dado de verdade não batia. Voltava, refazia, não batia de novo. Na terceira vez a diretoria cancelou o projeto.

A prática

Spec Engineering

Transformar evidências dispersas numa especificação revisável — e só então em código.

A spec não é documentação do que foi feito. É onde a divergência aparece antes de virar código.

Distinção importante

Não é "vibe coding"

Prompt diretoSpec Engineering
Entradao que você lembraas evidências, todas

Rastreio"por que está assim?"requisito → evidência → teste

Agente rápido sem spec não acelera o projeto. Acelera o retrabalho.

A unidade de trabalho

Requirement e Scenario

Uma spec é um contrato de comportamento. Cada cenário é um teste esperando para nascer.

### Requirement: Paciente sem identificador de negócio

O sistema SHALL retornar normalmente pacientes que não
possuam CPF nem CNS.

A ausência de identificador MUST NOT ser tratada como erro.
São 3,5% da base.

#### Scenario: Paciente sem CPF e sem CNS
- **WHEN** um consumidor solicita um paciente cujo registro
  tem `nr_cpf` e `nr_cns` nulos
- **THEN** o sistema retorna `200 OK` com um `Patient` válido
- **AND** o recurso não possui o elemento `identifier`
O ciclo

propose → apply → archive

/opsx:propose
Lê as evidências e produz proposal, specs, design e tasks. Para antes de implementar. Diante de ambiguidade material, pergunta em vez de escolher.
/opsx:apply
Implementa seguindo as tasks. Cada scenario da spec vira um teste.
/opsx:archive
A change vira spec permanente. A decisão de hoje continua localizável daqui a dois anos.

A fronteira entre planejar e implementar passa a ser do método — não da sua disciplina às onze da noite.

Antes do caso

Tudo o que vem a seguir é ficção

Os nomes
VitaFlow, Hospital Santa Aurora, Medsys e SIGH foram inventados para esta oficina. Qualquer semelhança com nomes reais de sistemas, empresas, hospitais, produtos ou pessoas é mera coincidência.
Os dados
Os 200 pacientes são gerados por algoritmo. Nenhum registro real de paciente foi usado, copiado ou anonimizado a partir de base existente.
Os documentos
A ata, os requisitos, o manual do fornecedor e o dicionário de dados foram escritos para o exercício. Não reproduzem documento de nenhum cliente.

Os nomes são fictícios. Os problemas, não.

Campo obrigatório que aceita nulo, domínio que ninguém documentou, carimbo de atualização que não atualiza — esses você reconhece.

O caso

VitaFlow × Hospital Santa Aurora

Uma healthtech precisa ler o cadastro de pacientes de um hospital que roda o SIGH, do fornecedor Medsys.

O fornecedor não fala FHIR. Entrega um Postgres e um manual de API de 2021 — para um sistema que está na versão 4.2.1.

Caso ficcional, dados sintéticos. As imperfeições do cadastro são reais.

Antes de implementar

Fachada, não repositório

JPA Server

Um repositório FHIR completo, com persistência própria. Exigiria copiar o cadastro para dentro dele.

Descartado. Levar prontuário para fora do hospital é exatamente o que a arquitetura proíbe.

Plain Server

Um IResourceProvider sobre a origem que já existe. O recurso é montado em memória a cada requisição.

Escolhido. A fachada é um tradutor. Nenhum dado sai do lugar.

Quase sempre dá para traduzir sem copiar. Migração costuma ser a resposta cara para a pergunta errada.

Achado durante os testes

A data de nascimento
andava um dia.

O banco tinha 1940-08-04. A API devolvia 1940-08-03.

// A data virava instante à meia-noite de America/Recife...
patient.setBirthDate(Date.from(
    data.atStartOfDay(ZoneId.of("America/Recife")).toInstant()));

// ...e o HAPI a serializava de volta no fuso da JVM.
// A máquina estava em America/Cayenne — UTC-4 até 1967.

Data de calendário não tem fuso. Converter para instante e voltar é o bug.

Em pareamento de paciente, um dia de diferença é identidade trocada. O teste de regressão está fixado no repositório.

Fechamento · passo 7

A spec vira documentação viva

Daqui a dois anos alguém vai perguntar por que tp_sexo = 'I' virou unknown e não other.

A resposta não está na planilha, nem na memória de quem já saiu da empresa. Está no requisito — com a evidência que a originou e o teste que a garante.

Para levar

O que fazer na segunda-feira

  • Junte as evidências antes de abrir o editor. Ata, requisito, manual, DDL — e o dado.
  • Rode a query. A afirmação mais confiante do projeto costuma ser a mais errada.
  • Escreva a divergência, não só a decisão. Quem vier depois precisa saber o que foi descartado, e por quê.
  • Deixe o agente perguntar. Ambiguidade resolvida em silêncio vira bug com paciente no meio.
  • Fachada antes de migração. Quase sempre dá para traduzir sem copiar.
